# 握手背压与性能损失的因果对照

2026-09-06，代码基线2cb6b27，模型未修改。用户指出FIFO同样背压，询问为何作业2没有额外性能损失。

输入固定为40条(30,30)，每条计算延迟1周期；D=1。使用build/debug/stage2_gcd.exe和stage1_gcd.exe，参数为INPUT OUTPUT STATS 1 - OUTPUT_PERIOD。三次运行均PASS，输出文件核对为40行30。

| 版本/输出周期 | 总周期 | 忙周期 | Compute结果等待 | 握手阻塞周期 |
|---|---:|---:|---:|---:|
| 作业2 / 1 | 84 | 40 | 0 | 0 |
| 作业2 / 13 | 520 | 40 | 425 | 451 |
| 作业1 FIFO / 13 | 520 | 40 | 425 | 无该指标，不代表无背压 |

fast/slow/fifo-slow文件分别保存实际功能和统计。此对照改变的是Output接收能力；不能把增加的436周期全叫作握手协议开销，更不能把425和451相加，它们包含重叠的等待。

基本八项的另一个对照：作业1为79周期，作业2为78周期，两者有效计算均66周期。作业2有53个valid&&!ready周期，却没有新增53个执行周期，因为大部分发送等待与Compute计算旧任务重叠。原边界FIFO被移除带来一拍传递差异，两个模型总容量不同，不能据此作等资源协议效率结论。

握手使流控显式化，FIFO接口原本已隐含可读/可写与保持规则。其性能价值在于可观察、可验证、可控的接口行为，不保证变快或变慢。Compute固有忙碌引起的上游等待，与Compute算完后被结果通道堵住，应分开解释。

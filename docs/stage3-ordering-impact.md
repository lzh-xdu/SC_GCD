# 作业 3：保序机制对性能及资源的影响

2026-09-08；基于当前源码及既有测试证据的分析，本轮未修改模型、未新增性能实验。

保序要求最终结果按输入编号输出，允许两个 Compute 乱序完成。它不改变单任务规定的 GCD 计算周期，但会影响完成后的等待、后续任务能否派发，以及系统吞吐。

## 性能影响与原因

- 队头阻塞：编号 0 尚未完成时，已经完成的 1、2 仍不能输出。结果驻留时间增加；等待是否延长总执行周期，还取决于它是否落在整体完成的关键路径上。
- 背压传播：旧版 Collector 只读下一编号对应的结果 FIFO；后续结果积压使 FIFO 满，Compute 留在 RESULT_PENDING，不能接收下一任务。新版将乱序结果收进窗口，释放结果 FIFO，但窗口信用耗尽时会停止新派发，即使 Compute 空闲。
- 固定传递代价：新版 Collector 每沿先退休旧槽，再接收新结果，新入窗口结果最早下一沿退休，比旧版增加一拍存储延迟。这是当前实现的代价，不是所有保序方案都必须增加一拍。
- 出口带宽：当前 Collector 每拍最多收一项、按序发一项，两个 Compute 不会使出口变成每拍两项。有限短任务或慢输出场景可能由出口限制；单拍退休是本实现带宽选择，不是保序在理论上只能单发射。

## 已有证据怎样解读

| 对照 | 已有结果 | 能支持的结论 |
|---|---|---|
| 旧版容量压力，R=1→2→4 | 总周期 663→648→648；两单元累计结果等待 74→7→0 | 增加结果缓存缓解背压，但等待减少不等于总周期等量减少，容量收益会饱和 |

## 资源代价

旧版利用严格轮转规律，以 nextId%2 选择下一结果通道，用两条结果 FIFO 暂存早完成项，控制简单，但与固定派发顺序绑定。新版增加按 id%W 寻址、完整编号校验的固定窗口、有效位、base/信用判断和收取仲裁，以支持择闲派发后的乱序完成。

当前 Result 的声明有效载荷是 64 位 id + 32 位 GCD = 96 bit。相同 D、R 下，窗口增加 96W bit 结果载荷及 W 个有效位，另有控制开销；W8 为 768 bit 载荷加 8 个有效位。预留信用覆盖所有已派发但未退休任务，不只覆盖已完成结果；最早慢任务始终有槽，避免后续结果填满缓存后拒收最早结果的循环等待风险。这是设计预防，不是已复现死锁。

默认旧版缓冲载荷 1088 bit，新版 W8 为 1856 bit，增加约 70.6%。这是包含 FIFO/流水槽的声明载荷比较，不是整个系统面积增加 70.6%。旧版 R6 同样为 1856 bit，可作等载荷比较，但控制不同，不能称等面积。第二个 Compute 属于并行计算资源成本，不应全部记为保序成本；id 也已存在，不应重复记成新版新增资源。

增加存储与控制可能增加面积、访问能耗及硬件时序压力，但本项目没有综合/功耗证据，不能给出实际面积、功耗或频率变化。C++ optional 对象大小、日志及统计样本内存也不能当硬件资源。

## 报告口径与后续分析建议

同时观察总周期/吞吐、端到端及 delivery 延迟、Compute 有效利用率、reorder_wait、结果等待、window_blocked_with_ready、窗口预留与完成结果占用。delivery 包含正常传输和下游等待，不全是保序开销；不同模块阻塞可能重叠，不可相加为损失周期，详见 [统计口径](task-statistics.md)。

现有实验能证明容量影响及两种架构的综合差异，尚不能给出“保序本身使吞吐下降 X%”。若需分离该代价，建议在相同调度、计算单元、缓存预算、出口带宽和输入下增加仅供分析的乱序输出对照；该对照不满足正式保序验收要求，尚未实施。保持保序的 W/R 单因素扫描可用于选择容量，但不能冒充保序开关对照。

# 作业 3：严格轮转双计算实例

2026-09-06，用户选择简单顺序分配与顺序结果处理；作业2基线75c76f5已独立验收。

Parser → FIFO(D) → 两级Transform → 轮转Dispatcher → 两个独立Compute → 各自结果FIFO(R) → 顺序Collector → FIFO(D) → Output。

Dispatcher 先0后1，只有成功握手才切换。被选单元忙时停住，即便另一单元空闲也不越过；组合路由只是接线，选择状态只在上升沿更新。无额外输入缓冲，不改变Transform两周期基础延迟。

Collector 按 next_id%2 读取对应结果FIFO，验证编号后写输出FIFO，每拍最多一项；无预取槽、不提前取走未获输出空间的结果。后完成的早编号结果可以独立进入自己的FIFO，避免单个共享队列被晚编号占头造成无法保序。结果槽容量有界，满时Compute保持自己的结果。作业2完成沿限制不变。

初始最小配置 R=1；主动场景将检查这种容量是否导致短结果迟迟不能交付、反向阻塞调度。若实际暴露性能设计缺陷，保留原配置数据，再比较增大R的资源代价；不为制造错误故意删去保持或顺序检查。

验证后更新（保留上面的初始设计）：B-006确认R=1在长短突发/慢输出下产生额外等待，默认改为R=2；R=4在同场景没有进一步缩短周期，故不继续增加默认容量。命令行仍可选择R=1复现原配置。

统计：每Compute任务数/忙周期/结果等待/利用率，总利用率=sum忙周期/(2*C)；轮转选中端阻塞且另一端空闲周期；Collector等待早编号而另一路有结果的周期、输出满阻塞；各缓冲容量/平均/峰值；Compute数、槽数、声明载荷容量。

与作业2同输入、D、输出节拍、编译配置比较 C2/C3 加速比、吞吐率及每Compute吞吐率。双实例多出每路结果缓冲和Collector，资源增加明确列出，不称等面积比较。严格轮转可能负载失衡，不能保证两倍速度；暂不改为择闲调度，以遵守用户选择。

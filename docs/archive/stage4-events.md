# 作业 4：无时钟事件模型

2026-09-10；用户要求本次提交移除全部时钟，并对比作业 3 的周期数量。基线采用作业 3 最终择闲窗口版本 `stage3_window_gcd`，资源、种子、输入和输出速率保持相同。

## 如何推进

`System::runEvents()` 是集中式事件调度器，不生成时钟、不按固定间隔轮询。各模块通过 `nextDelay()` 报告下一次可能发生状态转移的时间间隔，系统取最早者，交给 SystemC 的定时等待。无后续转移且尚未排空时报告死锁。

| 模块 | 下一个处理时刻 |
|---|---|
| Parser | 未 EOF 且输入 FIFO 有空位：下一个 1 ns 输入边界；满时不提供期限 |
| Transform | 能接收、推进一级或握手时：下一边界；被阻塞时不提供期限 |
| Dispatcher | 能握手时：下一边界；组合路由仍由信号变化触发 |
| Compute | BUSY：绝对完成时刻；待交付且有空间/空闲且可接收：下一边界 |
| Collector | 有结果可收或队首可输出：下一边界；只等待缺失队首或输出空间时不提供期限 |
| Output | 有结果时：严格晚于当前时刻的下一个输出服务时刻 |

生产路径中的 Parser 由 System 管理期限；其独立测试仍可使用原来的定时/FIFO 事件线程。两者无时钟端口，采用同一个读取校验方法。

每个事件批次调用模块的 `advance()`（Parser 为 `readAndSend()`），所有模块看到旧通道值，随后由 SystemC 更新 FIFO 和信号。这保留同拍 FIFO 释放不能立刻重用、新收结果不能同拍退休、计算完成不能同拍接新任务的约定。批次后等待三个零时间更新阶段，使当前拓扑的通道更新、组合路由及路由输出稳定；这不增加 ns，也不形成周期轮询。若未来增加组合路径层数，必须重新检查该稳定边界。

Compute 使用 `m_completeCycle = 接收时间 + 延迟`，没有逐周期递减计数器。所有 `sc_clock`、`m_clk`、边沿敏感注册与绑定均已移除；时间换算文件改名为 `model/timing/simulation_time.*`，1 ns 仅作为与作业 3 比较的周期单位。

## 统计和诊断

- 跳过区间使用 `accountSkipped()` 一次累计忙、空闲、阻塞周期；占用使用 `Usage::hold()` 累计“占用 × 持续周期”，不为统计增加定时唤醒。
- 保留正式结果/统计文件格式。控制台额外报告事件批次数和最大跳跃；批次数不等于 SystemC 全部进程唤醒数，也不等于模拟周期数。
- Trace 打开时按跳过区间补齐旧格式的逐周期阻塞行，最终按时间稳定排序；这些诊断行不参与仿真调度。Trace 关闭时不展开区间、不缓存事件行。详细 Trace 的内存与输出成本仍随展开行数增长。
- 新旧对比保留全部事件字段、时间及流内顺序检查；只隔离新增 `EVENT_SCHEDULER` 诊断行。本轮 31 个场景的事件 CSV 实际也逐字节一致。

Release/Debug 各 CTest 15/15。每种配置包括既有 31 个有效场景及 9 类非法输入的新旧对照、独立 Parser 测试，以及 4 个新增事件调度边界场景。全部对照的结果、周期和正式统计一致；Trace 开关不改变行为。

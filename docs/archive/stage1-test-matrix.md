# 作业 1：输出契约与扩展测试

2026-09-06，用户要求先完善作业 1，再推进握手。以下为已实施、已执行的验证。

## 输出分离

- `OUTPUT`：只有最终 GCD，每行一个非负十进制整数，保持输入顺序。INT32_MIN 的绝对值及 GCD 可以为 2147483648，结果不能用 int32 保存。
- `STATS`：独立的 `metric,value` CSV，包含总周期、任务数、吞吐率、计算忙周期/利用率、结果等待周期、FIFO 和流水寄存器容量/平均占用/峰值。
- `EVENTS`：可选调试 CSV，记录任务流转；不是功能结果，也不是完成通知的替代。
- 控制台：SystemC 提示和运行诊断；本轮将自有 PASS 摘要移至 stderr。重定向整个控制台不能代替指定 OUTPUT 文件。
- 三类文件原本已分开，本轮增加回归保障；并未新造一套统计或更改算法/时序。关闭 EVENTS 与开启时的功能、性能文件逐字节相同。
- 同路径输入/输出、功能/统计文件冲突均在打开前拒绝。非法输入和超时返回非零；失败时的部分结果不算成功交付。

## 检查方法与发现

所有成功场景均检查独立 GCD、任务数/顺序、两周期变换下界、Compute 精确延迟、完成沿不接新任务、FIFO 容量与同沿可见性；根据事件重算占用面积、峰值、忙周期、吞吐率与利用率。

扩展后每次完整回归包含 24 个有效场景、1434 个任务，另有关闭追踪对照、14 个非法输入、2 个路径冲突和超时。CTest 仍为 2 个入口，每个入口包含多项断言。

混合测试在相同深度 1、输出周期 1 下，比全短序列增加 221 个系统周期：其中新增有效计算 218 周期，新增 3 次任务接收开销。任务数也从 40 增至 43，因此不能把 306/85 当作纯粹的同工作量减速比。深度 4 没有缩短此序列总周期，单 Compute 的串行计算仍限制吞吐；这只是本测试结果，不能推广到所有负载。

首轮新增断言把深度 4 的峰值错误写死为 1，修正及证据见 [B-005](defects.md)。未发现新的处理器功能错误，不能拿这次测试资产错误充当作业 3/4 主动缺陷案例。

## 二、对 agent 方案的主要修改

用户判断改变 AI 方案方向的实例；两种等价方案间的取舍也如实记录。

1. **流水成员命名**：用户指出 m_stage1/m_stage2 与 namespace stage1 混淆 → 改 m_magnitudeStage/m_orderedStage（A-009/D-011）。
2. **Transform 更新顺序两次反转**：用户先指出倒序不利阅读，AI 改正向计算下一拍状态（D-018）；随后用户在背压传播讨论中明确选择倒序，AI 恢复并完善注释（D-019 替代 D-018）。两次均以用户判断为准，等价证据保留。
3. **择闲窗口死锁风险细化**：用户方案「窗口满则全停收」被 AI 分析出可能饿死最早结果返回，改为派发处预留 credit（D-016）；用户来源与 AI 细化分开记录，死锁为推理风险非已复现。
4. **「副本」语义纠正**：AI 误解为工程备份并创建 backups/，用户纠正为 src/stage4 内整合源码，AI 按纠正执行（作业 4 起点轮）。
5. **Parser 事件迁移节拍**：AI 表述「每个 delta 输入一对」被用户纠正，确认保持原输入节拍（每 1 ns 最多一对），AI 按空间事件解除阻塞实现（D-021）。
6. **结果 FIFO 默认容量**：AI 初选 R=1，被 B-006 主动测试数据修正为 R=2（663→648 周期），R=4 无进一步收益（D-014）。
7. **审查意见经核实后不盲改**：compute.hpp 顶部两个 @brief 经复核为 @file 与 @class 各自摘要（Doxygen 惯例），未改；开源审美 B 类（三层成员链、重型 Doxygen 等）与项目既有文档化决策相悖，用户确认只实施 A 类。
8. **日志比较适配**：全系统事件迁移新增 EVENT_SCHEDULER 诊断行触发旧测试整文件比较失败，修正为仅过滤该诊断行参与旧比较、新测试单独断言批次与跳跃（B-010），不放松正式结果/统计/事件断言。
9. **调度形式澄清**：用户质疑「SC_METHOD 改 data 敏感即可去 clock」，AI 对照代码澄清 route 仍是 SC_METHOD，完整事件方案还须处理完成期限、背压与输入节拍；集中式 runEvents 是实现取舍而非 SystemC 限制，分散事件方案为可行备选，未擅自重写。

## 三、发现 agent 实现问题时的判断与处理

### 处理原则

- **独立参考校验**：所有功能输出经 math.gcd 独立核对，AI 手写预期也靠它发现错误（B-003）。
- **先复现再修复**：修复前保留原始失败证据与版本基线（如 review-fixes 修复前 10/10 失败日志）。
- **归类不冒充**：区分测试资产错误、环境问题、AI 编辑错误、真实设计缺陷；只有后者计入作业 3/4 主动案例。
- **用户发现记为用户发现**：B-012/B-013 及三轮审查问题源自用户审查，不写成 AI 自查。

### 作业 3 主动案例：B-006 最小结果容量造成额外计算停顿

- 触发思路：严格轮转下短任务先完成但不能先输出，慢输出让其积压；初版每路 1 个结果槽可能把结果扣在 Compute 内。
- 复现（R=1，48 项压力输入）：663 周期、结果等待 74 周期，结果 FIFO 持续拥塞（平均占用 0.949/1）。
- 定位：compute_complete→compute_emit 差值累加与等待计数吻合；Collector 被早编号/慢输出限制反压至 Compute。
- 修正：R=2 后 648 周期、等待 7；R=4 无进一步改善 → 默认 R=2，容量对照固化进回归测试。
- 详见 [archive/defects.md](archive/defects.md)。

### 作业 4 主动案例：B-011 详细 Trace 使事件模型更慢且内存增长

- 触发思路：delta 轮次减少未必等于总耗时下降，主动用同输入成对开关 Trace 并测量耗时/内存。
- 实测（Windows 入口径）：混合小样本 Trace off 事件模型快 2.28×；Trace on 反慢 26.6%（32.3 vs 25.5 ms），峰值工作集 11.86 vs 5.65 MiB；Linux 复现同型退化（+481% vs +317%）。
- 定位：事件模型对跳过区间逐周期构造字符串控制行、缓存 vector、stable_sort 后写出；时钟模型直接写流。
- 状态：已复现、根因明确，修正建议（按事件批次增量写出/区间表示）未实施；功能时序不受影响。
- 详见 [archive/defects.md](archive/defects.md) 与 [archive/model-comparison.md](archive/model-comparison.md)。

## 2026-09-11：用户纠正 Trace 与采样的归类

- 用户指出 B-011 更像观测代码实现问题，当前 Trace 是打点而非采样。AI 核对代码后认可：EventRecorder 在任务/控制边界记录，并通过 repeat 展开跳过区间，属于事件打点和逐周期诊断日志，不是抽样式性能分析。
- 区分 Usage::sample/hold：前者读取占用，后者按持续周期加权累计，在模型时序契约下维持完整周期统计；它不是 B-011 中字符串缓存、排序路径。现有证据支持 Trace 实现开销问题，但未分离各函数耗时。
- B-011 应明确归为仿真观测/日志子系统的实现缺陷，不能写成事件驱动调度或被模拟硬件的功能缺陷。若题目案例限定模型核心，应另选或构造该范围的真实案例；本轮未新增实验或实施优化。

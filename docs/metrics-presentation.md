# 作业 1～4：统计指标与呈现方案

2026-09-10。来源：用户列出的四阶段最低统计要求。本文的具体公式、补充指标和图表是 AI 设计建议；本轮只做设计和源码核查，未新增计数器、生成实测图或运行性能实验，不改变阶段验收状态。

2026-09-10 晚更新：已按本文最小场景矩阵完成首轮实测（Linux/WSL 进程口径），数据、表图与结论见 [实测结果](metrics-results.md)；其中连续阻塞段以离线 Trace 导出完成，其余「新增」项的完成状态见其 §5。

## 1. 统一口径

- `T`：从模拟时间 0 到输入结束且系统排空的总执行周期，包含启动、EOF 检测与排空。保持当前实现边界，不改成首项到末项的间隔。
- `N`：Output 最终收到的任务数；正常结束核对输入有效任务数与输出数相等，并检查结果、编号顺序、丢失和重复。
- `τ`：一个模拟周期的时间长度；模拟时间为 `T×τ`。事件模型沿用同一时间单位，事件批次数不等于执行周期。
- `B_i`：第 i 个 Compute 的有效计算周期，不含结果等待；`K_j`、`q_j(c)`：缓冲 j 的容量及第 c 个周期更新稳定后的占用。
- 所有平均值默认覆盖完整运行。事件模型用 `Σ(占用×持续周期)/T`，不能对事件时刻直接做算术平均；峰值也必须覆盖真实状态变化。
- 比率同时标明分母和单位。分母为零时新派生指标显示 N/A；现有 CSV 的空任务延迟、无 valid 时阻塞比例仍保留既定 0，并在报告注明“无样本”。
- 配置栏至少记录：输入/哈希、任务数、计算实例数、FIFO 深度 D、结果 FIFO 深度 R、窗口 W、输出节拍、随机种子、模拟周期、模型版本、构建模式及 Trace 设置。不适用参数填“—”。

下文“已有”指核查当前源码或已有测量报告；“派生”可从现有数据计算；“新增”需要补充观测，不能当成已测数据。

## 2. 作业 1：完成多少、花多久、资源用了多少

| 指标 | 公式/统计口径 | 呈现及当前覆盖 |
|---|---|---|
| 总执行周期、模拟时间 | `T`；`T×τ` | 总览卡；已有 `cycles`、`simulated_time_ns` |
| 处理任务总数 | `N`，以最终输出为准 | 总览卡及正确性检查；已有 `tasks` |
| 平均吞吐率 | `N/T`，任务/周期；需要时另换算任务/模拟秒 | 总览卡；已有 `throughput_tasks_per_cycle` |
| Compute 有效利用率 | `B_0/T` | 利用率条形图；已有 `compute_busy_cycles`、`compute_utilization` |
| 计算资源未做有效工作的原因 | 无输入周期、结果等待周期，各列次数及占 T 比例 | 并列条形图；已有计数。它们不是现成的互斥状态分解 |
| 缓冲容量、平均占用、峰值 | `K_j`、`Σq_j(c)/T`、`max q_j(c)` | 每条 FIFO、Transform 流水槽逐行列出；已有 `*_capacity/average/peak` |
| 缓冲平均/峰值占用率 | 平均占用/K；峰值/K | 派生，按百分比比较不同容量 |
| 缓冲满载占比（补充） | `Σ1[q_j(c)=K_j]/T` | 新增；峰值达到满容量不代表长期满载 |
| 任务延迟（补充） | Output 接收时刻−Parser 发送时刻，报告均值/P95/最大值 | 已有 `task_latency_end_to_end_*`；不含进入 Parser 前的等待 |

缓冲表模板：`资源名称 | 容量（项） | 平均占用（项） | 峰值（项） | 平均占用率 | 满载占比（待新增）`。作业 1 的资源名称为 Parser→Transform、Transform→Compute、Compute→Output、Transform 流水寄存器。

主计算资源以 Compute 为主。Transform 流水槽占用反映存储使用，不能直接叫计算利用率；若要分别评价取绝对值、比较交换的计算利用率，须新增各级实际执行操作的周期计数。

推荐正文一张总览表、一张缓冲表、一张 Compute 利用率图。零延迟任务可能有吞吐但忙周期为 0，说明它没有题目定义的取余工作，不代表系统没处理任务。

## 3. 作业 2：阻塞发生在哪、持续多久、是否影响整体性能

继承作业 1，缓冲表按实际拓扑更新；valid/ready 链路不是一条新的 FIFO。

| 指标 | 公式/含义 | 呈现及当前覆盖 |
|---|---|---|
| 握手阻塞周期 S | 每沿 `valid && !ready` 累加 | 已有 `handshake_blocked_cycles` |
| 有效请求阻塞率 | `S/V`，V 为 valid 周期数 | 已有 `handshake_blocked_fraction`；回答“有任务要传时，有多少比例被挡住” |
| 全程阻塞占比 | `S/T` | 派生；与 S/V 分开标注 |
| Compute 结果等待 | `Σ(E−C)`，C 为计算完成、E 为写入结果 FIFO | 已有 `compute_result_wait_cycles` 及任务 `result_wait` 均值/P95/最大值 |
| 空闲但没有输入 | `idle_no_input_cycles/T` | 派生；包含启动、排空和供给不足，不能全部归因于背压 |
| 连续阻塞段（补充） | 每次由非阻塞进入阻塞算一段；段数、平均长度、最长长度 | 新增汇总；详细逐周期 Trace 完整时也可离线导出 |
| 性能变化 | 同输入对照 `T`、吞吐、端到端 P95、缓冲占用 | 由实际实验派生；不能从 S 推算周期损失 |

建议实验：同输入固定其他参数，分别改变一个 FIFO 深度或输出节拍。输出对照表：`配置 | T | 吞吐 | S/V | S/T | 结果等待 | 端到端 P95`。

图形采用“横轴容量/输出节拍、纵轴吞吐”的折线图，阻塞率放相邻小图，不使用难读的双纵轴。选一小段 Trace 画任务时间线，展示“输出变慢→结果滞留→上游握手受阻”。

不同模块阻塞可能重叠；现有 Compute 忙周期与完成沿的写出失败也可能同时计数，且接收沿未必属于已有忙/空闲计数。不可把这些计数堆叠为总和 100% 的状态图。若需要这种图，必须新增按同一采样边界定义的互斥状态分类。

作业 1→2 的周期差包含接口和传输节拍变化，不能命名为“消除阻塞节省的周期”。单因素配置实验也应写清改变的是哪个因素。

## 4. 作业 3：并行收益与保序代价

| 指标 | 公式/含义 | 呈现及当前覆盖 |
|---|---|---|
| 两实例任务量与利用率 | `N_0,N_1`；`U_0=B_0/T,U_1=B_1/T` | 已有 `compute0/1_tasks/utilization`；两行对照 |
| 双实例平均利用率 | `(B_0+B_1)/(2T)` | 已有 `compute_utilization`；不能用忙周期之和/T 作为 0～100% 利用率 |
| 负载不均衡程度 | `abs(B_0−B_1)/(B_0+B_1)`，零工作量 N/A | 派生；同时展示任务数，任务数均衡不代表计算负载均衡 |
| 双实例相对单实例加速比 | 同输入 `S_2=T_single/T_dual` | 派生；同时报吞吐增长 `(Q_dual/Q_single−1)×100%` |
| 并行效率 | `S_2/2` | 派生；仅在基线说明充分时解释，阶段架构有变化时不是纯第二实例收益 |
| 队头保序等待 | 后续结果已就绪、应退休编号尚未就绪的周期 | 已有 `reorder_wait_cycles`；同时报占 T 比例 |
| 下游输出阻塞 | 队头可退休但 Output FIFO 满的周期 | 已有 `collector_output_blocked_cycles`，与保序等待分列 |
| 窗口限制 | 信用耗尽周期；其中仍有 Compute 可接收的周期 | 已有 `window_blocked_cycles`、`window_blocked_with_ready_cycles` |
| 窗口使用 | 预留项数与已完成结果项数的平均/峰值，分别除 W | 已有 `window_reserved_*`、`window_results_*`；预留也包含尚未完成任务 |
| 保序等待的任务级分布（补充） | 从结果进入窗口到退休的驻留时长，均值/P95/最大值 | 新增边界观测；驻留仍包含正常传输/下游等待，不全算纯保序损失 |
| 保序资源代价 | 结果载荷 `96W bit`，有效位 `W bit`，控制字段单列 | 当前窗口已有相关指标；完整硬件面积/功耗未经综合，不能量化 |

正文安排两张表：

1. `场景 | 单实例T | 双实例T | 加速比 | 并行效率 | U0 | U1 | 缓冲payload bits`。
2. `W/R | T | 吞吐 | 保序等待 | 窗口阻塞且算力可用 | 预留峰值 | 结果峰值 | payload bits`。

推荐两张图：各场景单/双实例周期分组柱状图；窗口容量与吞吐/存储代价的上下对齐小图。长短任务偏斜时附少量任务的 Compute0/1 完成和 Collector 按序退休时间线。

对照分三类，标题不可混用：

- 阶段 2 单实例 vs 阶段 3 双实例：展示整机架构升级收益，明确 Collector、缓存、调度也可能变化。
- 同一双实例架构下 W 或 R 单因素扫描：展示容量如何影响保序和吞吐；旧轮转→择闲窗口是综合架构比较。
- 若要单独量化“强制保序”的代价：另做仅供分析的乱序输出对照，固定调度、实例数、缓存预算、出口带宽及其余时序。该对照尚未实施，且不满足正式按序输出验收；不作为本轮新增实现要求。

详细资源边界及历史证据见 [保序影响](stage3-ordering-impact.md)。不要把第二个 Compute、已存在的 id 或主机 C++ 对象大小全部记为新增保序硬件。

## 5. 作业 4：模型等价与仿真成本分表

基准采用 `stage3_window_gcd` 与对应事件模型 `stage4_gcd`；输入、结构参数、延迟规则、输出节拍和统计设置一致。

| 比较维度 | 必报指标 | 判断方式与覆盖 |
|---|---|---|
| 功能结果 | 结果值、数量、编号顺序、丢失/重复 | 独立 GCD 参考校验，两模型逐项一致；已有验证 |
| 系统时间和性能 | T、模拟 ns、吞吐、任务延迟、两实例利用率、阻塞、缓冲占用 | 整数计数精确一致；显示比例可受舍入影响。比较完整统计而非只比较总周期；已有 |
| 关键时序（补充） | P/A/C/E/O 五个事件边界的任务时间戳 | 同 id 同边界一致；不要求无语义依赖的日志行任意全局排序相同 |
| 仿真执行效率 | 模型入口墙钟耗时、进程耗时；`T/墙钟秒`、`N/墙钟秒` | 模拟周期/主机秒、任务/主机秒；已有耗时，可派生速率 |
| 仿真加速比 | `median(t_clock)/median(t_event)` | >1 表示事件模型更快；不得称为硬件吞吐提升 |
| CPU 开销 | 进程用户态+内核态 CPU 时间 | 已有；低于计时分辨率时标明限制 |
| 内存开销 | 峰值工作集、峰值私有提交内存 MiB | 已有；与硬件 payload bits 分开 |
| 调度开销解释 | 内核 delta 轮次、模型事件批次、跳过周期比例 | 已有；不是总事件通知/进程唤醒数，跳过比例不是时间加速比 |
| Trace 开销 | 同输入同模型的 on/off 耗时、内存、文件大小 | 已有部分场景；报告绝对差及耗时增幅 `(t_on/t_off−1)` |

建议正文分为：

1. 等价表：`场景 | 功能PASS/FAIL | T：时钟/事件 | 吞吐：时钟/事件 | 完整统计一致性`。有差异时列首个不一致任务/字段及原值，不用平均误差掩盖功能错误。
2. 效率表：`场景 | 时钟ms [Q1–Q3] | 事件ms [Q1–Q3] | 加速比 | 任务/主机秒`。
3. 开销表：`场景 | CPU ms | 峰值工作集 | 峰值commit | delta轮次 | 事件批次 | Trace大小`，每项并列两个模型。

推荐图：各场景主机耗时的分组柱状图和四分位区间；加速比图标出 1× 参考线并保留退化场景。跨度过大时使用清楚标注的对数轴。已有 [实测报告与图](model-comparison.md) 可直接复用，历史数字需保留原基线，不能冒充修改后重测。

测量沿用已有方法：同机同 Release 构建，预热 1 次、正式 7 次、交替顺序串行运行，保存原始样本，报告中位数及 Q1–Q3。模型入口耗时包含构造、仿真、统计及文件 I/O，不标成纯 `sc_start`；详细 Trace 默认关闭，开销实验再成对打开。7 次重复不报告稳定的主机耗时 P95。

## 6. 最小实验矩阵和交付物

| 场景 | 主要回答的问题 | 适用阶段 |
|---|---|---|
| 空输入、单任务、零计算延迟 | 边界、分母、启动/排空是否处理正确 | 1～4 |
| 连续短任务、连续长任务 | 传输/出口瓶颈与计算瓶颈 | 1～4 |
| 固定种子混合任务 | 一般负载、延迟分布与负载均衡 | 1～4 |
| 慢输出、小缓冲，逐个改容量 | 背压传播和缓冲收益饱和 | 2～4 |
| 首项长、后续短；长短偏斜 | 队头等待、调度不均、窗口信用限制 | 3～4 |
| 长等待、连续短任务，Trace on/off | 事件稀疏收益、事件密集退化和日志成本 | 4 |

这些是报告组织建议，不表示本轮执行了全部组合。已有实测可链接引用；新增场景与观测项先实施再填数。

保留已有 `stats.csv` 和可选事件 CSV；建议报告脚本另导出：每运行一行的 `runs.csv`、每资源一行的 `resources.csv`、每次主机测量一行的 `profiling_samples.csv`。所有文件以 run_id 关联配置/版本，不改变现有报表格式即可先完成整理。

优先级：先用已有计数和派生公式完成四阶段总览及对照表；需要深入解释瓶颈时再补满载占比、连续阻塞段、窗口驻留时间。统计只能观察状态，不参与流控和调度。

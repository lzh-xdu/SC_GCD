## L-016：`BOUNDARY_COUNT` 是统计边界数量，不是普通局部 const

- 2026-09-10，用户澄清上一轮所问对象是 `TaskStatistics::BOUNDARY_COUNT`，而不是项目中全部 `const` 局部变量；AI 据此改为围绕任务生命周期统计解释。
- `BOUNDARY_COUNT = 5` 对应五个按顺序记录的事件：`parser_send`、`compute_accept`、`compute_complete`、`compute_emit`、`output`。它同时决定单任务时间线数组长度、统计样本数组长度和完成判定阈值。
- 五个边界产生四段相邻延迟（precompute、compute、result_wait、delivery），再额外记录一项首末相减的端到端延迟；因此统计输出有五组数据而非五段串联时间。
- `constexpr` 表示该值可在编译期使用，`static` 表示它属于 `TaskStatistics` 类型而不是每个对象各存一份，`private` 则限制其只服务于类内部的存储布局和逻辑。
- 随后用户要求继续列举全部同类变量；范围明确为当前 stage4 及其共享实现中的所有 `constexpr`，并区分项目配置、模型协议、统计标签和函数内算法常量。

## L-014：从代码追踪握手发布与零延迟交付

- 2026-09-08，用户追问代码依据，并提出“一个周期内完成直接deliver”的理解。
- Transform 在第3沿把旧 magnitude 槽移入 ordered 槽，再调用 valid/data.write；信号在该时间点的 update 阶段生效。Compute 仅敏感于 posedge，所以不会因 valid 改变再次运行，第4沿才通过 valid&&ready 调用 accept；与同沿两个进程的执行先后无关。
- b=0 不进入 gcdAndLatency 的 while，latency保持0；accept 直接记录complete、设 RESULT_PENDING 并调用deliver。准确表述为“接收沿同一仿真时间完成”，没有推进一个周期。
- deliver 只是尝试nb_write，FIFO满则保持结果待交付；成功后下游也只能在后续上升沿读取。普通C++函数执行耗费主机时间，但不自行推进SystemC仿真时间；非零任务也先算数值，再由后续tick倒计时表达规定延迟。
- 依据当前 src/stage2/transform.cpp、compute.cpp；仅代码讲解，未修改模型或重跑测试。用户理解尚待后续验证。

## L-010：背压计数不是额外总执行周期

- 用户正确指出FIFO也会阻塞上游，并质疑显式握手未产生额外性能影响。
- 澄清：FIFO隐含流控、握手显式流控；在同一瓶颈限制下可以有相同吞吐。缓冲可容纳更多等待任务，不能提高串行Compute固有服务能力。
- valid&&!ready只说明发送端有任务未获接收，可能与Compute处理旧任务重叠；不可把该计数加到计算忙周期上估算总周期，也不能把阻塞率当作吞吐损失百分比。
- 当前基本输入作业2有53阻塞周期、66忙周期、总78周期；作业1为79周期，一拍差源于移除中间FIFO。前述报告没有强调这种因果区别，本轮补充。
- 同40条(30,30)、D=1，作业2输出周期1→13使总周期84→520，结果等待0→425，握手阻塞0→451；作业1慢输出同样520。真实对照见evidence/stage2-blocking。
- 高阻塞并非总是坏事：当Compute仍高利用率地计算，背压是供给超过服务能力的表现；当结果等待高、有效计算利用率降低，应检查下游瓶颈。用户尚未进一步复述确认。

## L-004b：从 C++ 到 SystemC，再到电路

原编号 L-004；2026-09-06 审核消除重复编号，内容保留。

- 2026-09-06 用户要求面向三年 C++ 经验、已知时钟和信号概念的初学者进行完整讲解；以下为 AI 教学结论，尚无用户掌握情况的验证。
- SystemC 通过 C++ 类型、模块/端口/通道、进程和离散事件内核表达硬件结构与并发；普通编译生成主机仿真程序。SC_THREAD 是可挂起的仿真进程，不等于 GPU 执行线程或必须并行运行的操作系统线程。
- 普通赋值立即生效；sc_signal 写入在更新阶段生效。同一模拟时刻可以有多轮 delta 调度，不能把 delta 当成物理门延迟，也不能认为任意组合链等待一个 delta 就全部稳定。
- 信号本身不必对应寄存器：组合敏感进程与时钟触发进程表达不同硬件；位宽、跨周期状态和读写行为决定硬件含义。复位行为需要明确描述，仿真默认初值不能替代真实复位。
- 功能模型、周期模型和 TLM 选择不同抽象层次。架构模型可用主机立即计算结果再安排未来完成，但需要单独建模容量、占用、接收间隔和反压；模型设定的延迟不是电路实测结果。
- 延续 D-006：模型可以作为人工 RTL 实现的规格/参考，也可以在符合指定工具可综合子集和约束时，经 HLS 生成 RTL。HLS 再经逻辑综合与物理实现才到芯片版图；FPGA 则映射已有资源并生成配置位流。仿真可执行文件、测试平台和 VCD 不会直接变成电路。
- HLS 需要调度运算、分配/共享资源、保存跨周期状态并生成控制逻辑。延迟与启动间隔 II 是不同指标；循环次数、C++ 语句数和 wait(ns) 均不能直接当作硬件周期数或物理实现保证。
- 核对依据：本地 SystemC 3.0.1 内核与信号源码、现有 day01 示例；[Accellera 综合子集说明](https://www.accellera.org/activities/working-groups/systemc-synthesis)、[Siemens Catapult](https://www.siemens.com/en-us/products/ic/catapult-high-level-synthesis/hls/c-cplus/)、[HLS 架构与调度手册](https://docs.altera.com/r/docs/683152/current)、[OpenROAD 实现流程](https://openroad-flow-scripts.readthedocs.io/en/latest/user/UserGuide.html)。
- 本轮只做概念讲解和记录，未修改模型、未运行新测试或综合，也未提前实现任何作业阶段。

## 2026-09-10：仿真时间与事件期限

- 对“系统时间由事件及对应处理延迟推进”的解释：仿真内核推进至最近待处理时刻；4 ns 接收、6 ns 延迟意味着 10 ns 完成，若 5 ns 有其他输入则先处理该输入。执行 C++ 数值计算本身不增加仿真时间。
- 去掉时钟保留 1 ns 的比较单位，不把 delta cycle 当物理延迟。新模型的总周期仍为模拟耗时/1 ns；事件批次数表示实际选择了多少处理时刻，两者不同。
- [事件模型](archive/stage4-events.md) 的单任务为 13 个模拟周期、8 次事件批次；百万周期慢输出仍花费百万模拟周期，但无需每周期调用模型。未据此断言主机性能或用户已掌握。

## 2026-09-10：SC_METHOD 与事件调度不是互斥选择

- 用户追问为何不把 clock 敏感项直接换成 data。AI 澄清：SC_METHOD 可以响应信号或显式事件；Stage4 的 Dispatcher::route 仍使用 SC_METHOD。SC_METHOD 不能 wait，但可以通过 next_trigger 或定时 sc_event 安排后续调用；选择 SC_THREAD 不是事件驱动的必要条件。
- 数据值变化不等于事务接收：valid、ready、FIFO 可用空间、输入节拍及内部完成期限都可能决定状态推进。重复数值写入 sc_signal 不一定产生变化事件；本项目 Payload 比较包含 ID，因此不同 ID 的相同操作数会变化，不能据此断言现有模型丢重复任务。
- 仅把时钟敏感项改为 data 会遗漏内部完成和解除背压事件，也可能把原来跨周期的传输压到同一模拟时刻的多个 delta。保留原节拍需要显式的定时与握手协议。
- 当前 System::runEvents 汇总 nextDelay、等待最近期限、在同一求值阶段调用各 advance，再让通道更新及组合路由稳定；跳过区间通过 accountSkipped 加权统计。advance 是普通 C++ 成员函数，时间由外围 wait 推进。
- 分散的 SC_METHOD + 到期/通道事件同样可行，模块自治更强；当前集中方案便于旧时序对照，但依赖集中期限维护和固定 delta 稳定步骤，每次仍调用各模块，不保证执行效率优于分散事件方案。这里是代码解释与备选设计，未批准或实施架构重写，未记为用户已掌握。

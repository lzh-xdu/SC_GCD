# 过程记录方式

目标：让审阅者看清需求如何变成设计、实现如何被验证、问题如何被修正。记录实际工作，不追求日志篇幅。2026-09-11 文档精简后入口如下。

## 文件分工

| 文件 | 记录内容 | 更新时机 |
|---|---|---|
| [status.md](status.md) | 阶段验收、待定事项、仓库发布状态 | 阶段或阻塞状态变化 |
| [work-log.md](work-log.md) | 时间顺序的进展摘要、修改、验证、下一步 | 每次实质工作结束前 |
| [ai-log.md](ai-log.md) | AI 协作三方面：向 agent 提出的重要设计要求、对 agent 方案的主要修改、agent 实现问题的判断与处理（含缺陷案例 B-006/B-011） | 发生有价值的协作事件 |
| [learning-log.md](learning-log.md) | 用户实际回答、概念纠正、待验证理解 | 学习产生可复用结论 |
| [coding-style.md](coding-style.md) | C++ 风格规则与项目例外 | 风格约定变化 |
| [final-design.md](final-design.md) / [metrics-results.md](metrics-results.md) | 最终技术设计与实测报告 | 设计或测量结论变化 |
| evidence/ | 小型测试输出、性能原始数据和复现说明 | 实际执行验证后 |
| [archive/](archive/) | 已融合或被替代的历史文档，只读 | 不再更新 |

编号约定：D=设计决策、A=协作事件、B=缺陷（编号沿用历史记录；新的协作事件与缺陷直接记入 ai-log.md 对应小节，不必新开文件）。

## 一轮工作的最小闭环

1. 开始：明确所属阶段、目标与需要验证的行为。
2. 决策：有重要取舍时在 ai-log.md 或 work-log.md 记录来源（题目/用户/AI）、选项与状态。
3. 实施：完成一个小改动；发现问题先记现象与证据，不等到修好才写。
4. 验证：记录命令、输入、配置、预期、实际、退出码及版本。未执行就写未执行。
5. 沉淀：工作日志链接相关记录，更新阶段状态。
6. 版本：检查后提交该工作单元。公开远端确定后推送并核对可访问性。

纯文档变更只需核对内容和链接，无需重新运行无关代码测试。

## Git 与证据约定

- 提交消息使用 `stage1: ...`、`stage2: ...`、`docs: ...`、`test: ...` 等直观前缀。
- 可复现证据注明代码基线提交；若测试包含未提交修改，明确列出，不伪称基线已含这些修改。
- 证据与改动同提交时写"本条所在提交"，不预填无法事先知道的提交哈希。
- 初始化前的工作只能补记，不能伪造过去日期的 Git 提交。
- 日志先保留摘要，关键失败可保存完整小型输出；大波形和构建日志按需要筛选，不一概上传。
- 公开远端未设置前，本地文件和本地提交均不满足"公开可访问"要求，状态持续保持待完成。

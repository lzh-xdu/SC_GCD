# 过程记录方式

目标：让审阅者看清需求如何变成设计、实现如何被验证、问题如何被修正。记录实际工作，不追求日志篇幅。

## 文件分工

| 文件 | 记录内容 | 更新时机 |
|---|---|---|
| [status.md](status.md) | 阶段验收、待定事项、仓库发布状态 | 阶段或阻塞状态变化 |
| [work-log.md](work-log.md) | 时间顺序的进展摘要、修改、验证、下一步 | 每次实质工作结束前 |
| [decisions.md](decisions.md) | 设计问题、选项、取舍、决定、验证依据 | 设计确定或改变 |
| [ai-log.md](ai-log.md) | 重要 AI 要求、建议、用户判断、AI 错误 | 发生有价值的协作事件 |
| [learning-log.md](learning-log.md) | 用户实际回答、概念纠正、待验证理解 | 学习产生可复用结论 |
| [defects.md](defects.md) | 缺陷及其复现、修复证据；阶段 3/4 案例 | 发现、定位、修正问题 |
| evidence/ | 小型测试输出、性能原始数据和复现说明 | 实际执行验证后 |

## 一轮工作的最小闭环

1. 开始：明确所属阶段、目标与需要验证的行为。
2. 决策：有重要取舍时登记 D 编号，注明是谁提出及当前状态。
3. 实施：完成一个小改动；发现问题就登记 B 编号，不等到修好才写。
4. 验证：记录命令、输入、配置、预期、实际、退出码及版本。未执行就写未执行。
5. 沉淀：工作日志链接 D/B/A 等记录，更新阶段状态。
6. 版本：检查后提交该工作单元。公开远端确定后推送并核对可访问性。

纯文档变更只需核对内容和链接，无需重新运行无关代码测试。

## 简短模板

### 工作记录

日期/阶段；目标；修改文件；关联决策/AI/缺陷编号；验证命令与结果（或未运行原因）；尚未解决；下一步。

### 设计决策 D-xxx

问题；来源（题目/用户/AI）；选项；选择及理由；代价；状态（提议/已决定/已实施/已验证/被替代）；关联代码/测试/替代编号。

### AI 协作 A-xxx

重要要求；AI 建议或实现；用户实际反馈或修改；发现的问题；处理；证据；尚待用户判断。

### 缺陷 B-xxx

阶段与状态；为何想到场景；输入/容量/调度/版本/命令；预期；实际及原始证据；原因分析；修正；回归；遗留限制。

## Git 与证据约定

- 提交消息使用 `stage1: ...`、`stage2: ...`、`docs: ...`、`test: ...` 等直观前缀。
- 可复现证据注明代码基线提交；若测试包含未提交修改，明确列出，不伪称基线已含这些修改。
- 证据与改动同提交时写“本条所在提交”，不预填无法事先知道的提交哈希。
- 初始化前的工作只能补记，不能伪造过去日期的 Git 提交。
- 日志先保留摘要，关键失败可保存完整小型输出；大波形和构建日志按需要筛选，不一概上传。
- 公开远端未设置前，本地文件和本地提交均不满足“公开可访问”要求，状态持续保持待完成。
